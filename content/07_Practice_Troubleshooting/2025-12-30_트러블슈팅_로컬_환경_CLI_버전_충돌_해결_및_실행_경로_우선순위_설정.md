# 로컬 환경 CLI 버전 충돌 해결 및 실행 경로 우선순위 설정

---

## 1. 🚨 문제 현상 (Problem)

**이슈:** 터미널에서 `gemini` 명령어를 입력할 때, 사용자가 의도한 `npx`를 통한 **최신 버전(Latest Version)**이 아닌, 과거에 전역 설치된 **구버전(Legacy Binary)**이 실행되는 문제가 발생했습니다.

**증상:**
*   명령어: `gemini`
*   기대 결과: `npx @google/gemini-cli`에 의한 최신 기능 실행
*   실제 결과: `/usr/local/bin/gemini` 또는 `~/.npm-global/bin/gemini` 경로에 있는 오래된 실행 파일이 구동됨

**시스템적 의문점:**
Shell이 명령어를 해석할 때 `PATH` 환경 변수의 순서에 따라 어떤 바이너리를 선택하는지, 그리고 `npm` 전역 설치 패키지와 시스템 레벨(`/usr/local/bin`)에 수동으로 설치된 바이너리 간의 우선순위 충돌이 어떻게 발생하는지에 대한 원인 규명이 필요했습니다.

---

## 2. 🕵️‍♂️ 탐색 및 추론 흐름 (Investigation Trail)

문제의 원인을 파악하고 최적의 해결책(항상 최신 버전 사용)을 도출하기 위해 다음과 같은 단계적인 진단을 수행했습니다.

### Step 1: 실행 파일의 실제 위치 추적 (Path Tracing)
가장 먼저 Shell이 `gemini`라고 입력했을 때 어느 경로를 참조하는지 확인했습니다.

*   **명령어:** `which gemini` 또는 `command -v gemini`
*   **발견 사항:**
    1.  `~/.npm-global/bin/gemini`: npm 전역 설치 경로에 의해 생성된 바이너리.
    2.  `/usr/local/bin/gemini`: 시스템 전역 경로에 존재하는 레거시 바이너리.
*   **분석:** `/usr/local/bin`이나 `.npm-global/bin`이 `PATH` 환경 변수의 앞단에 위치하여 `npx`보다 먼저 참조되고 있음을 확인했습니다.

### Step 2: 충돌 요소 식별 및 제거 시도 (Conflict Resolution)
가장 먼저 npm을 통해 설치된 전역 패키지를 제거하여 `npx` 경로를 비워보려 했습니다.

*   **명령어:** `npm uninstall -g @google/gemini-cli`
*   **결과:** `~/.npm-global/bin/gemini`는 제거되었으나, 문제는 지속됨.
*   **추가 탐색:** `/usr/local/bin/gemini` 존재 확인. 이 파일은 버전이 매우 낮았으며, 시스템 권한으로 보호되어 있어 일반 사용자 권한으로는 삭제가 불가능한 상태였습니다.

### Step 3: 우선순위 역전 전략 수립 (Priority Inversion Strategy)
레거시 파일을 물리적으로 삭제하는 것(`sudo rm`)은 권한 문제로 인해 자동화 스크립트에서 수행하기 어렵거나, 시스템 안정성상 리스크가 있을 수 있습니다. 따라서 **"물리적 삭제"** 대신 **"논리적 우선순위 변경"**을 택했습니다.

*   **접근 방식:** Shell Alias(별칭) 기능 활용.
*   **로직:** 사용자가 `gemini`를 입력하면, Shell이 PATH를 검색하기 전에 미리 정의된 `npx @google/gemini-cli` 명령어로 치환하여 실행하도록 설정.
*   **검증:** `.zshrc` 설정 파일에 `alias gemini='npx @google/gemini-cli'`를 추가 후 `source ~/.zshrc`로 적용.

### Step 4: 잔여 파일 정리 및 최종 확인 (Cleanup)
사용자가 직접 `sudo` 권한으로 레거시 파일을 삭제한 이후, `npx`의 동작 방식을 최종 확인했습니다.

*   **현상:** 최초 실행 시 `Need to install...` 메시지가 출력됨.
*   **분석:** `npx`는 로컬에 패키지가 없을 때마다 최신 버전을 다운로드(Fetch)하여 캐시에 저장 후 실행하는 방식입니다. 따라서 최초 1회 다운로드 메시지는 정상적인 동작(Install-on-the-fly)이며, 이후 실행부터는 캐시된 버전이 사용되거나 새 버전이 있을 때만 업데이트됩니다.

## 3. 🛠️ 해결 및 패턴화 (Resolution & Optimization)

이번 트러블슈팅을 통해 도출된 해결 방안과, 동일한 문제가 발생했을 때 사용할 수 있는 최적화된 터미널 파이프라인을 정리합니다.

### 해결 방안 요약
1.  **기존 충돌源 제거:** `npm uninstall -g <package>` 및 `sudo rm /usr/local/bin/<binary>`를 통해 물리적 충돌 요소 제거.
2.  **Shell Alias 설정:** `.zshrc`에 별칭을 등록하여 `npx` 실행을 기본 동작으로 강제.
3.  **설정 적용:** `source ~/.zshrc` 또는 터미널 재시작.

### 최적화된 터미널 파이프라인 (Optimized Pipeline)
앞으로 유사한 CLI 버전 충돌이 발생했을 때, 상황을 진단하고 해결하는 효율적인 명령어 조합입니다.

```bash
# 1. 현재 어떤 바이너리가 실행되는지 확인 (Which)
#    심볼릭 링크인 경우 실제 경로까지 추적
which gemini
readlink -f $(which gemini)  # Linux/WSL
ls -l $(which gemini)        # macOS (심볼릭 링크 확인)

# 2. npm 전역 패키지 확인 및 제거
#    -g 옵션을 사용하여 전역 설치 리스트에서 해당 패키지를 찾아 제거
npm list -g --depth=0 | grep gemini
npm uninstall -g @google/gemini-cli

# 3. 시스템 레벨 레거시 파일 제거 (주의: sudo 필요)
#    /usr/local/bin에 남아있는 수동 설치 파일을 제거
sudo rm /usr/local/bin/gemini

# 4. 영구적인 우선순위 설정 (Shell Alias)
#    npx를 통한 항상 최신 버전 사용 보장
#    파이프라인을 사용하여 .zshrc 파일 끝에 alias 자동 추가
echo "alias gemini='npx @google/gemini-cli'" >> ~/.zshrc

# 5. 설정 즉시 반영
source ~/.zshrc

# 6. 최신 버전 정상 작동 테스트
gemini --version
```

## 4. 📌 나만의 Action Item (Playbook)

로컬 개발 환경에서 **"Always Latest"** 전략을 유지하기 위해, CLI 도구 버전 충돌이 의심될 때 기계적으로 수행해야 할 3단계 계획입니다.

### Phase 1: 진단 (Diagnosis)
도구가 의도치 않은 동작을 할 때, 실행되고 있는 실체 파일의 경로를 확인합니다.
```bash
# 예상치 못한 구버전이 실행될 때
which <command_name>
file $(which <command_name>)
```

### Phase 2: 정화 (Purge)
전역 설치된 패키지와 시스템 경로의 잔여 파일을 모두 제거하여 깨끗한 상태를 만듭니다.
```bash
npm uninstall -g <package_name>
# 시스템 경로에 수동으로 설치된 흔적이 있다면 제거
sudo rm /usr/local/bin/<command_name>
```

### Phase 3: 우회 및 최신화 (Bypass & Update)
매번 설치하지 않고, 실행 시점에 최신 버전을 가져오도록 `npx`와 `alias`를 결합하여 방어 로직을 구축합니다.
```bash
# ~/.zshrc 또는 ~/.bashrc에 추가
alias <command_name>='npx <package_name>@latest'

# 변경 사항 적용
source ~/.zshrc
```
