# 터미널 환경 CLI 바이너리 버전 충돌 및 레거시 경로 정리 (Troubleshooting Playbook)

## 1. 🚨 문제 현상 (Problem)

### 기술적 난제
사용자가 터미널에서 `gemini` 명령어를 입력할 때, 의도한 최신 버전의 CLI(`npx @google/gemini-cli`)가 아닌, 과거에 시스템 전역 경로(Global Path)에 설치된 **레거시 바이너리(Legacy Binary)**가 우선 실행되는 현상이 발생했습니다.

### 최초 인지 및 증상
*   **증상:** `npx`를 통해 최신 버전을 사용하려는 의도와 달리, 단순히 `gemini`를 입력하면 구버전이 호출됨.
*   **알럿/로그:**
    *   `/Users/a1234/.npm-global/bin/gemini` (NPM 전역 설치 경로)
    *   `/usr/local/bin/gemini` (시스템 레벨 경로, 아주 오래된 버전 `[FILTERED_JWT]` 존재)
*   **시스템적 의문점:**
    1.  왜 `npx`의 패키지가 아닌 전역 설치된 바이너리가 `PATH` 순위에서 우선하는가?
    2.  `npm` 전역 패키지를 삭제했음에도 불구하고, `/usr/local/bin`에 남아있는 심볼릭 링크나 실행 파일이 어떻게 명령어를 가로채는가?
    3.  시스템 파일(`/usr/local/bin`)의 삭제 권한(Sudo)이 없는 상황에서, 권한 문제를 우회하여 사용자가 올바른 도구를 사용하게 하려면 어떤 우회로(Shell Trick)를 사용해야 하는가?

## 2. 🕵️‍♂️ 탐색 및 추론 흐름 (Investigation Trail)

### 1단계: 실행 경로 추적 (Path Tracing)
*   **의도:** 현재 쉘이 `gemini`라는 명령어를 입력받았을 때 어디서 실행 파일을 찾고 있는지 확인.
*   **명령어 흐름:** `which gemini` 또는 내부 경로 분석.
*   **단서:**
    *   `/Users/a1234/.npm-global/bin/gemini`가 확인됨.
    *   이는 과거에 `npm install -g @google/gemini-cli`를 수행했던 흔적임.

### 2단계: 패키지 의존성 확인 및 제거 (Inventory & Cleanup)
*   **의도:** NPM 레벨에서 설치된 전역 패키지를 확인하고, `npx`와의 충돌을 원천 봉쇄하기 위해 전역 패키지 삭제.
*   **명령어:** `npm list -g --depth=0` -> `npm uninstall -g @google/gemini-cli`.
*   **결과:** NPM 전역 패키지는 삭제되었으나, 문제가 완전히 해결되지 않음.

### 3단계: 잔존 레거시 파일 발견 (Residual Check)
*   **의도:** NPM 삭제 후에도 문제가 지속되므로, OS 레벨의 기본 경로(`/usr/local/bin`)에 다른 설치 흔적이 있는지 확인.
*   **명령어:** `/usr/local/bin/gemini` 경로 확인.
*   **단서:**
    *   `/usr/local/bin/gemini`에 매우 오래된 버전의 바이너리/링크가 존재함.
    *   AI가 직접 삭제(`rm`)를 시도했으나, `Permission denied` (권한 부족)로 인해 삭제 실패. 이는 `sudo` 권한이 필요한 시스템 영역임을 의미.

### 4단계: 우회로 전략 수립 (Alias Override)
*   **추론:** 파일을 물리적으로 지우는 것(시스템 수정)은 권한 문제로 어렵거나 위험할 수 있음. 대신, 쉘 설정 파일(`.zshrc`)에서 **명령어 우선순위(Command Alias)**를 높여서 레거시 파일을 무시하고 항상 `npx`를 호출하도록 설정하는 것이 안전하고 유지보수에 유리함.
*   **검증:** `.zshrc`에 `alias gemini='npx @google/gemini-cli@latest'`를 추가하여, 사용자가 `gemini`를 타이핑하면 쉘이 이를 `npx ...`로 자동 변환하도록 설계.

### 5단계: 최종 해결 및 검증
*   **사용자 행동:** `sudo rm /usr/local/bin/gemini`를 통해 사용자가 직접 레거시 파일 삭제 수행.
*   **결과:** `gemini` 입력 시 `npx`가 패키지를 다운로드(`Need to install...`)하고 최신 버전이 실행됨. `alias` 설정이 정상 작동하고 있음을 확인.

## 3. 🛠️ 해결 및 패턴화 (Resolution & Optimization)

### 인프라 이슈 최적화 (Infrastructure Optimization)

AI가 수행한 탐색 과정은 정확했으나, 명령어를 여러 번 분리해서 실행하는 비효율이 있었습니다. 이를 **원샷(One-shot) 파이프라인**으로 최적화하는 방법을 제시합니다.

#### ❌ 비효율적인 탐색 (Before)
```bash
which gemini
npm list -g
ls /usr/local/bin/gemini
# (각각 별도의 실행 블록으로 접근)
```

#### ✅ 효율적인 터미널 파이프라인 (After)
**명령어 정의(`type -a`)와 정보 추출을 결합하여 즉시 상황을 파악합니다.**

```bash
# 1. 해당 명령어에 대해 쉘이 인지하는 모든 경로와 타입을 한 번에 출력
type -a gemini

# 2. 시스템 바이너리의 실체를 확인 (파일인지 링크인지, 버전은 무엇인지)
ls -lh /usr/local/bin/gemini 2>/dev/null || echo "No system binary found"

# 3. 전역 NPM 패키지 중 충돌 가능성이 있는 항목만 필터링하여 빠르게 확인
npm list -g --depth=0 | grep -i gemini
```

#### 🛡️ 솔루션 패턴: Alias를 이용한 "Soft Delete"
시스템 파일을 삭제(`sudo rm`)하는 것은 권한 문제뿐만 아니라, 다른 패키지 매니저(Homebrew 등)가 관리하는 파일일 경우 의존성 깨짐을 유발할 수 있습니다.
**`.zshrc` 또는 `.bash_profile`에 별칭(Alias)을 등록**하여 물리적 삭제 없이 논리적으로 우선순위를 바꾸는 방식이 가장 안전합니다.

```bash
# .zshrc 추가 내용
# 레거시 바이너리가 있더라도 무시하고 항상 최신 npx 버전 사용
alias gemini='npx @google/gemini-cli@latest'
```

## 4. 📌 나만의 Action Item (Playbook)

동일한 CLI 버전 충돌 또는 레거시 바이너리 잔재 문제가 발생했을 때, 기계적으로 수행할 수 있는 **3단계 표준 절차**입니다.

### Step 1: 명령어 출처 전수 조사 (Full Audit)
쉘이 해당 명령어를 어디서 찾는지 모든 가능성을 확인합니다.
```bash
type -a <command_name>
```
> *해석:* `type -a`는 Alias, Function, Built-in, PATH 순으로 모든 후보를 보여주어 충돌 지점을 즉시 발견하게 해줍니다.

### Step 2: 패키지 매니저 정리 (Package Cleanup)
Homebrew나 npm 등 패키지 매니저를 통해 설치된 전역 버전을 제거합니다.
```bash
# NPM의 경우
npm uninstall -g <package_name>

# Homebrew의 경우
brew uninstall <package_name>
```

### Step 3: 쉘 설정 강제 오버라이드 (Shell Override)
시스템 파일의 삭제 권한이 없거나 삭제가 위험한 경우, 쉘 설정 파일에 Alias를 추가하여 사용자 의도대로 실행되도록 강제합니다.
```bash
# ~/.zshrc 또는 ~/.bashrc에 추가
alias <command_name>='<preferred_execution_command>'

# 설정 즉시 반영
source ~/.zshrc
```
